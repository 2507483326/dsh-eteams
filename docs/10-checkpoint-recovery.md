# 10 断点续行完整方案（上下文不丢失）

> 用户核心关切：「任务中断后可以继续执行」「断点续行如何保证每个成员执行时上下文不会丢失，需要一个更加完整的计划」。本文是该计划的完整版本，覆盖 D7（进程重启冷恢复）以及随子代理机制自带的基础能力（会话内中断继续）。

## 10.0 设计哲学：三层真相 + 一条铁律

**三层真相**（互为备份，层层兜底）：

| 层 | 载体 | 保存什么 | 谁保证 |
|---|---|---|---|
| L1 成员会话层 | DSH 子代理持久会话（storages） | 成员全部对话历史（执行过程的原始上下文） | DSH `dsh-subagent`（机制自带） |
| L2 任务状态层 | `.eteams/<teamId>/team.json + events.jsonl` | 任务/尝试/执行线路/决策/邮箱（协作结构状态） | 本插件（[09](09-persistence.md)） |
| L3 工作区产物层 | 工作区文件系统 | 已产出的代码/文档/数据（副作用结果） | 成员遵守幂等纪律（10.6） |

**铁律：任何时刻，仅凭 L2+L3 即可重建「可继续的工作」；L1 让继续时的成员「记得做过什么」。** 因此 L2 的执行线路 + 交接包（[07](07-scheduling.md) 7.6）必须自含：即使 L1 彻底丢失（子代理会话损坏），换成员 + 交接包仍能继续任务，只是失去原始会话记忆。

## 10.1 中断场景分类与续行矩阵

| # | 场景 | 表现 | 续行路径 | 上下文损失 |
|---|---|---|---|---|
| S1 | 用户打断执行中的成员（普通停止） | attempt->paused，成员子代理保留 | 领队发消息续行：同 attempt `resumed`，`followup` 唤醒原会话 | 无（L1 完整） |
| S2 | 成员轮次异常终止（超限/工具故障） | 同 S1（停驻） | 同 S1；连续异常由领队改派 | 无 |
| S3 | DSH 进程崩溃/重启 | 全部内存态消失 | **冷恢复**（10.4）：磁盘重建 + 成员重挂 + 遗留 attempt 处理 | 无（L1/L2/L3 均持久） |
| S4 | 成员子代理会话损坏/被清理 | followup 报 NOT_RESUMABLE | 换成员 + 交接包（L2 兜底） | 失去原会话记忆，结构状态完整 |
| S5 | 任务失败重试 | 旧 attempt failed | 同成员新 attempt（续会话）或换成员（交接包） | 无 / 同 S4 |
| S6 | 领队会话中断（用户关窗重开） | 领队邮箱滞留未读 | DSH 会话机制续存；重开补投未读（10.5） | 无 |
| S7 | 任务执行到一半被取消 | attempt revoked | 终态，无需续行 | - |
| S8 | 跨会话打开旧团队 | - | **v0.2 非目标**（D7）；数据模型预留 `captainSessionId` 与归档只读 | - |

## 10.2 L1：成员会话层（为什么上下文天然不丢）

成员 = durable continuable subagent（`ctx.subagents.startContinuable` 派生）。DSH 子代理机制保证：

1. 每个成员的对话历史持久存储于 DSH storages（与主会话同存储体系），**跨轮次、跨进程重启**。
2. 唤醒 = `ctx.subagents.followup(captain, childId, [message])`：在**同一会话**上追加新轮次--成员记得之前的一切（含执行中的思考、读过的文件、踩过的坑）。
3. 打断 = `ctx.subagents.interrupt(childId)`：当前轮停止，会话与已写状态保留。
4. 因此「同成员续行」不依赖任何插件侧的上下文搬运--插件的职责是**把「该谁继续什么」这个协作事实持久化**（L2），并在正确时机发出 followup。

本插件在其上追加的保证：
- attempt 与成员绑定关系持久（team.json）；attemptToken 防过期会话迟到写。
- 停驻（paused）语义：interrupt 后插件立刻把 attempt/成员状态落盘（S1 路径的磁盘一致性）。

## 10.3 L2：任务状态层（断点 = 执行线路的最新事件）

**断点的定义**：任务的执行线路（attempts+events）最后一条事件就是权威断点：

```
t3: a5 [claimed 14:00] [progress 14:07 已完成数据模型] [progress 14:15 导出接口草稿]
                  ^-- 崩溃于此。断点 = "导出接口草稿"之后
```

- 每次状态/进度变更**先落盘再继续**（[09](09-persistence.md) 不变量 1），因此断点最坏滞后一个崩溃窗口的「一次通知」（9.6），不滞后已确认状态。
- **续行消息的组装**（同成员，S1/S3）：
  ```
  [续行] 任务 t3 的 attempt a5 从中断处继续。
  中断点：你最后的进度是「导出接口草稿」（14:15）。
  请先核对当前工作区状态（文件可能比你记忆的更新或更旧），再继续执行；
  已完成的步骤不要重复执行（幂等纪律见任务合同）。
  ```
- **换成员续行**（S4/S5-reassign）：交接包（[07](07-scheduling.md) 7.6）= 断点 + 前史摘要 + 产物清单。交接包在 claim 时落盘进新 attempt 首事件（自含审计）。

## 10.4 L3 配套：冷恢复流程（S3 完整步骤）

触发：会话激活（用户重开会话 / DSH 启动装载会话）时，插件按 `captainSessionId` 扫描工作区状态根。

```
1. 扫描 .eteams/*/team.json（+ archive 跳过）→ 属于本会话的团队集合
2. 逐团队执行 recovery（持 team 锁）：
   a. 校验/修复快照与日志（9.4/9.7）
   b. 团队 phase 恢复：staged→照旧等待批准；paused→照旧；
      running→进入「恢复对账」：
   c. 成员重挂：对每个 status ∈ {working, paused} 的成员：
      - 子代理存在且可续（followup 探活）→ 标记 reattached，保持 paused
      - 不存在/NOT_RESUMABLE → 任务走换成员路径（交接包），记 recovery.attempt_stale
   d. 遗留 attempt 处理：running 的 attempt 一律先转 paused（绝不自动续跑，
      防止重启后盲目重放副作用）；由领队（或用户在面板）逐个确认续行
   e. retrying 的退避定时器重建（用持久化的 nextRetryAt，不用内存计时）
   f. 邮箱补投：领队/成员各自的未读消息在下次唤醒前先投
   g. recovery.cold_started 事件落盘（含对账结果摘要）
3. 面板/卡片呈现恢复报告：「已恢复团队 X：3 成员重挂、1 任务待确认续行、2 条未读」
4. 领队收到系统消息，按协议向用户简报并继续协调
```

关键决策：

- **恢复不自动续跑**：所有进行中 attempt 恢复为 paused 等待显式确认。理由：冷重启后环境（进程、网络、终端）都变了，盲目续跑违背幂等纪律；显式确认让领队/用户有机会先核对。配置项 `autoResumeOnColdStart: false`（默认），高级用户可开。
- **不重复有副作用的操作**：续行消息强制要求成员「先核对再继续」（10.3 模板）；工具层不拦截（无法静态判定副作用），纪律在协议 + 交接包中三重强调（成员协议 7.8、续行模板、交接包建议栏）。

## 10.5 L1 领队侧：会话续存与消息补投

- 领队 = 主会话，DSH 会话本身持久（S6 天然覆盖）。
- 插件在领队每次轮次边界（模型步开始处）检查邮箱未读并注入补投（在线即投模型）；确保「重启期间成员完成的通知」不丢（NFR 至少一次投递 + 幂等消息 id）。
- 领队协议提示词常驻「当前活动团队摘要」（团队名/阶段/待决策数），冷启动后首轮自动重注入，领队不会「失忆」。

## 10.6 L3 工作区产物层：幂等纪律

成员协议与任务合同模板强制：

1. **产物即真相**：重要中间结论写文件；标准载体是任务文件夹的 `notes.md`（D12：插件只建不写，成员追加），不只留在会话里（会话可能换人）。
2. **先核对再执行**：接取/续行/重试的第一步都是核对工作区当前状态（列出已存在产物），再决定从哪继续。
3. **可重入命令优先**：安装用幂等方式（`pnpm install` 而非手工下载）、生成用覆盖式、外部副作用（发邮件/部署）显式声明不可重入。
4. **changedPaths 诚实申报**：完成/失败时申报变更文件，交接包据此构造核对清单。
5. **任务文档三件套（D12）**：README/contract.md 是状态的幂等渲染视图（丢失可重建，不承载增量信息）；notes.md 是成员增量记忆（交接包与冷恢复必读，[07](07-scheduling.md) 7.6）；恢复时前者自动重渲染、后者原样保留。

插件侧配套：任务合同模板含「幂等性」栏（领队拆解时填写该任务的副作用风险与核对命令）。

## 10.7 保证与不保证（诚实边界）

| 保证 | 依据 |
|---|---|
| 已确认的任务终态永不丢失 | 事件先落盘 + 原子快照（09） |
| 进行中任务的结构状态（谁/做到哪/为什么中断）永不丢失 | 执行线路即断点（10.3） |
| 同成员续行时记得全部执行历史 | L1 子代理持久会话（10.2） |
| 换成员续行时获得结构化完整交接 | 交接包（7.6）+ L2 兜底（10.0 铁律） |
| 重启后团队可恢复且不盲目重放副作用 | 冷恢复流程 + paused 确认制（10.4） |

| 不保证（v0.2） | 说明 |
|---|---|
| 成员崩溃瞬间的「未落盘思考」 | 最后一次 progress 之后的过程性思考会丢（有 L1 时通常仍在会话里；会话损坏则丢） |
| 多进程并发写同一团队 | 单写者假设（NFR-03），冲突检测报错 |
| 跨会话恢复/并行团队 | D3/D7 明确非目标 |
| 副作用命令的强幂等 | 纪律性保证（协议+模板），非执行层拦截 |

## 10.8 验证方案（对应 [16](16-testing-acceptance.md)）

1. **单测**：断点快照重放（构造事件序列 → 崩溃 → 重放 → 断言状态）；attemptToken 吊销后更新被拒；退避定时器重建。
2. **verify 脚本**：模拟冷恢复全流程（伪造 running 团队 → recovery() → 断言成员 reattached/attempt paused/未读补投）。
3. **手工 GUI 清单**：三个杀进程实验（成员执行中杀 / 重试等待中杀 / staged 杀）+ 两个打断实验（停成员后续行 / 停领队后补投），全部要求恢复后零任务丢失、零重复副作用（人工核对 changedPaths 与产物）。

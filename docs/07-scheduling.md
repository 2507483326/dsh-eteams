# 07 调度与协调（领队全主导模型）

本文定义 D4 决策（领队全主导）下的完整协作流程、消息契约与通知机制。是 [11 工具 API](11-tools-api.md) 的行为规范。

## 7.1 模型总述

```
用户 ──目标──▶ 领队 ──拆解──▶ 任务清单(staged) ──用户批准──▶ running
                        │
        ┌───────────────┼───────────────────────────────────┐
        ▼               ▼                                   ▼
     指派 t1→成员A    指派 t2→成员B                      汇总与汇报
        │               │                                   ▲
        ▼               ▼                                   │
     成员A 接取→执行→站点汇报完成 ─通知─▶ 领队同轮双动作：推进链(指派t3下一站) + 给成员A派下一任务 │
        │                                   │                            │
        └── 失败→自动重试(08)→超限→awaiting_decision→挂起/换人/通知用户 ────┘
```

核心规则（领队协议，注入系统提示词）：

1. **领队不执行**：任何任务执行都必须指派给成员；领队没有执行工具（FR-07）。
2. **一步一指派**：每个就绪任务由领队显式指派给具体成员，默认执行链下一站（D11）；不存在自动接取池（D4）。
3. **完成必回报**：成员任务/站点终态（完成/失败/阻塞）必经邮箱通知领队；领队收到后决定「下一步谁执行」（FR-17），并**同轮给刚空闲成员指派下一任务**（完成即续派，FR-36）。
4. **并行靠多指派**：无依赖任务领队可同时指派给不同成员并行执行；同一成员同一时刻只持有一个活动 attempt。
5. **用户指派等同**：面板指派与领队指派走同一状态机；领队必收到系统通知（D10/FR-18）。

## 7.2 阶段一：团队创建与任务拆解

1. 激活：`/eteams <目标>` 或自然语言（「用团队模式…」）-> 领队协议注入。
2. **问询细节（FR-37，领队人设固定纪律）**：拆解前领队就目标向用户做一轮结构化提问：交付形式与受众、范围边界与非目标、验收偏好、风格/技术约束、优先级与敏感点。答复要点写入对应任务合同（问询记录进事件日志）；用户明确「直接开始」可跳过。
3. `eteams_create_team`：落盘 TeamState（phase=staged），生成默认领队（即当前会话）。
4. `eteams_add_member`×N：成员占位（staged，未派生子代理）；各成员可指定模型路由（缺省继承当前对话路由快照，FR-08）；按角色生成默认人设（可编辑，D13）；头像种子即生成（FR-09）。
5. `eteams_create_task`×N：任务草案（draft）+ 依赖（写入即查环）+ **执行链**（D11）。拆解要求（注入提示词）：
   - 每任务：一句主题 + 合同（目标/验收/范围/非目标）+ 显式依赖 + 执行链（站点序列：成员 + 阶段说明）；
   - 任务粒度：单站点单成员单次会话可完成；不确定就拆；
   - 执行链规划：常见形态「调研 -> 实现 -> 审校」按需裁剪；单站任务直接指定执行人；
   - 收敛到「最小有用 DAG」：能并行尽量并行（不同任务的链首站可同时开工）。
6. 领队宣布计划就绪，等待用户在面板（staged 编辑器）审阅/编辑/批准。领队**不得**自行批准（与参考实现同边界）。
7. 用户批准 -> `plan.approved` 事件 -> **创建任务文件夹并生成 MD 文档**（README + 每任务 contract.md；workDir 记入 TeamState，FR-38）-> 成员子代理**原子派生**（一次循环内全部 spawn；失败整体回滚到 staged 并报错）-> draft->ready 刷新 -> phase=running。

> 批准也可显式跳过（`eteams_create_team` 传 `approval:'automatic'`），用于高级用户/脚本场景；默认 required。

## 7.3 阶段二：指派-接取-执行-汇报循环

### 7.3.1 指派（领队 -> 成员）

领队调用 `eteams_assign_task(taskId, member, deviation_note?)`，带链任务可直接 `eteams_advance_task(taskId)`（默认指派链下一站，D11）：

前置校验：task∈{ready}（依赖满足）、成员 ready、团队 running；指定非链下一站成员时 `deviation_note` 必填（[06](06-task-lifecycle.md) 6.7 偏离）。动作：

1. task->assigned，生成 attempt(kind=initial, status=pending_accept, token)。
2. 投递**指派消息**到成员邮箱并唤醒（在线即投 `followup`）。

指派消息模板（kind=assignment）：

```
[指派] 任务 t3「实现导出模块」 · 站点 2/3（实现）
阶段说明：基于 t1 调研结论完成导出模块实现与自测
合同：
  目标：…
  验收：…（可测条目列表）
  范围：src/export/**（不得改动 config/**）
依赖产物：
  - t1 完成：docs/竞品矩阵.md（摘要：…）
执行要求：
  1. 调用 eteams_claim_task(task_id, attempt_id) 接取任务（生成你的执行线路）。
     若无法接取，调用 eteams_decline_task(attempt_id, reason) 拒接并说明。
  2. 执行中有阶段性进展用 eteams_append_progress(attempt_id, text) 记录；
     重要结论同步写入任务笔记 notes.md（交接与恢复素材，D12）。
  3. 完成调用 eteams_complete_task(attempt_id, {output, changedPaths})；
     失败调用 eteams_fail_task(attempt_id, error)——可重试失败请如实报告。
  4. 全程可通过 eteams_task_board() 查看全团队任务状态。
attempt_id: a5   token 随 claim 下发
```

### 7.3.2 接取（成员 -> 团队）

`eteams_claim_task(task_id, attempt_id)`：校验 attempt 归属与状态 -> attempt->running、task->in_progress、成员->working；执行线路追加 `claimed` 事件；返回 token 与完整上下文（合同 + 交接包，见 7.6）。

拒接：`eteams_decline_task(attempt_id, reason)` -> attempt->revoked、task->ready（回到待指派）、通知领队（含理由）。领队改派或与用户商量。

> 「接取」的意义（原始需求）：确认握手 + 执行线路的起点 + 凭证发放，使执行记录从此刻开始可审计。

### 7.3.3 执行与进度记录

- 成员按合同执行；阶段性进展 `eteams_append_progress`（≤200 字/条，见 [06](06-task-lifecycle.md) 6.3）。
- 成员可 `eteams_send_message` 向领队提问（question 消息；领队在线即见，否则邮箱待投）。
- 成员可 `eteams_task_board()` 查看全队任务状态（FR-15，返回紧凑文本表格）。

### 7.3.4 汇报（成员 -> 领队）

终态三选一：

- 完成 `eteams_complete_task(attempt_id, {output, changedPaths})` -> completed；汇报消息（kind=report）含 output 摘要。
- 失败 `eteams_fail_task(attempt_id, error)` -> 进入重试阶梯（[08](08-retry-escalation.md)）。
- 阻塞声明（不终态）：成员发 question 消息说明阻塞；任务保持 in_progress，领队决定继续等待/改派/取消。

汇报消息模板（kind=report）：

```
[汇报] 任务 t3「实现导出模块」 站点 2/3 完成（attempt a5，用时 23m）
产出：src/export/index.ts + 单测；changedPaths: [src/export/**, tests/export.spec.ts]
摘要：<成员 output 的前几行>
下一步（按执行链）：站点 3/3 审校员「验收」--可调用 eteams_advance_task 一键推进
成员B 现已空闲：可接 t4（其为链首站）或由你另行指派（完成即续派，FR-36）
```

> 末站完成时模板标题为「任务 完成」并无下一站行。模板中「下一步」「空闲提示」是成员/系统的**建议权**，决策与指派动作由领队完成（D4）；完成即续派是领队人设固定纪律（FR-36）。

### 7.3.5 领队决策（收到汇报后）

领队被唤醒（在线即投/邮箱补投），执行「下一步路由」：

1. 读汇报与任务板（`eteams_team_status`）。
2. 决策（同轮完成双动作，FR-36）：
   a. **推进刚完成的任务**：默认 `eteams_advance_task`（链下一站）；需要时偏离（assign + deviation_note）或修正计划（新增/取消任务，D5 运行中编辑）。
   b. **给刚空闲的成员指派下一任务**：按任务板挑选其适合的任务（其链首站/角色匹配）；确无合适任务则明确回复让其待命。
3. 循环 7.3.1。

全部任务终态 -> 领队汇总最终报告（对话内输出 + 卡片标记 completed）。

## 7.4 多团队切换与归档（D3）

- **切换** `eteams_switch_team(teamId)` / 面板切换器：当前团队 phase=paused（活动 attempt 全部停驻，成员 paused）；目标团队激活（phase=running；paused 成员按需恢复）。会话内同一时刻只有一个 running 团队（per-captain 锁保证）。
- **归档** `eteams_archive_team(teamId)`：非 running 团队整体搬移 `archive/`，只读；活动团队必须先完成/停止才能归档。
- 团队列表与切换入口：面板顶部切换器（活动 + 暂停 + 新建）；对话内亦可自然语言切换。
- 每个团队独立成员集与邮箱（FR-05 上下文隔离）：切换后领队协议上下文带当前活动团队 ID，工具自动路由。

## 7.5 通知机制（notifier 规范）

| 事件 | 通知对象 | 通道 | 时机 |
|---|---|---|---|
| task.assigned | 成员 | 邮箱 + followup 唤醒 | 指派落盘后 |
| task.report（完成/失败终态） | 领队 | 邮箱 + followup 唤醒（若领队轮次进行中则排队至模型步边界） | 终态落盘后 |
| task.awaiting_decision | 领队 | 同上 + 事件流 | 重试超限（08） |
| user.assign（面板指派/拖拽入槽） | 领队 | 系统消息（kind=system）：「用户已将 t3 指派给成员B」 | ops 落盘后 |
| user.message（成员对话框直发，D15） | 成员 | 邮箱 + 空闲即唤醒（执行中排队至本轮结束） | 发送落盘后 |
| task.cancelled（进行中被取消） | 执行成员 | 系统消息 + interrupt 打断当前轮 | 吊销后 |
| decision.resolved | （无）事件流记录 | - |

投递语义（与参考实现一致）：至少一次；在线即投；离线滞留邮箱，成员/领队下次唤醒先补投未读（`readUnreadMailbox`）。幂等键 = 消息 id。

## 7.6 交接包（Handoff Bundle，FR-28）

当任务需要**换人**（reassign / 换人重试 / 接管恢复）时，新成员接取时的上下文不止合同，还有结构化交接包：

```
[交接包] 任务 t3「实现导出模块」（第 2 任执行人）
之前发生了什么：
  - a1（成员B，13:40-13:58）：失败——依赖版本冲突；进度：已定位冲突源 pom.xml
  - a2（成员B，14:02-14:11）：失败——test_export 断言失败；进度：已写 6/9 用例
当前工作区状态：
  - 已有产物：tests/export.spec.ts（6 用例）、src/export/draft.ts
  - 声明变更：见各 attempt.changedPaths
  - 未提交/未验证内容：draft.ts 未过类型检查
相关消息：与领队的 2 条问答（摘要）
建议：先跑 pnpm test tests/export.spec.ts 确认基线，再续写 3 个用例
```

组装规则（`prompts/handoff.ts`）：任务合同 + 前序 attempts 的进度/失败摘要（每尝试 ≤5 条关键事件）+ 最后一次 outcome + changedPaths 并集 + notes.md 尾部摘要（≤10 行，若成员有记，D12）+ 相关 question/answer 消息摘要 + 上一任成员的建议（若有）。交接包随 claim 返回，也写入新 attempt 的首事件（保证线路自含）。

> 交接包是「断点续行不丢上下文」在**跨成员**维度的答案；同成员续行靠子代理持久会话（见 [10](10-checkpoint-recovery.md)）。

## 7.7 领队人设（固定框架，D13）

领队人设 = 统一人设框架（[05](05-data-model.md) PersonaRecord：角色定位/职责/风格/技能/纪律/执行提示）+ 领队专属**固定纪律段**。默认模板内置；用户可经面板人设编辑器或 `<workspace>/.eteams/captain-persona.yaml` 修改（框架字段固定，保证结构化编辑；修改于下一段注入生效）。注入内容（`prompts/persona.ts` + `prompts/captain.ts`，分段、带激活边界）：

1. **触发**：`/eteams` 命令、自然语言团队意图、或已有活动团队时的新用户消息。
2. **拆解纪律（D12）**：先问询后拆解（FR-37 问题清单）；拆解必含执行链规划（D11）；批准即建任务文件夹并生成文档；staged 边界（不自行批准）；成员设计（角色覆盖、最小人数、人设可定制）。
3. **指派纪律**：默认沿链推进（advance）；偏离必附原因；**完成即续派**（同轮给空闲成员派下一任务，无合适任务明确让其待命，FR-36）；一次一任务一成员；并行指派先声明。
4. **决策规范**：收到完成汇报 -> 先看任务板再决定下一步；失败升级的处置顺序（08）；挂起时主动告知用户影响面（哪些下游被阻断）。
5. **汇报规范**：阶段里程碑主动向用户简报（≤5 行）；最终汇总必含：产物清单、各任务执行线路摘要、遗留风险。
6. **禁止**：执行任务、跳过用户批准、私聊成员让其「偷偷开工」（成员协议同样拒绝无 attempt 的工作请求）。

## 7.8 成员协议（执行提示模板要点）

`prompts/member.ts`（spawn 时注入 + registerContinuableSetup 工具面）：

0. **人设基线（D13）**：spawn 时注入人设全文；每次唤醒消息头部附人设摘要（人设修改后下次唤醒生效）。人设定义行为风格，任务合同优先于风格偏好。
1. 只做被指派且已接取（claim 成功）的任务；无 attempt 的工作请求一律回复需要正式指派。
2. 执行线路纪律：阶段节点必记 progress；重要结论同步写入任务 notes.md（D12）；失败如实报告（附复现要点）。
3. 最小上下文：不主动打听其他任务；需要跨任务信息走 question 消息问领队。
4. 汇报模板（7.3.4）；完成后立即空闲等待（不自行续做下游）。
5. 边界：遵守工作区沙箱与审批策略；不改合同范围外文件（inScope 声明时）。

## 7.9 反模式与防护

| 反模式 | 防护机制 |
|---|---|
| 领队自己「顺手」执行任务 | 领队工具面无执行工具；成员工具对领队隐藏（参考实现同策略） |
| 成员互相私派任务 | 指派只能由领队/用户触发；成员间消息不改变任务状态 |
| 领队批量指派同一成员多任务 | 同一成员仅一个活动 attempt；第二个指派被拒（提示先等完成或改派他人） |
| 成员完成但不汇报 | 完成工具调用即生成 report 事件（协议双保险：工具副作用+提示词） |
| 领队长时间不决策 | awaiting_decision 在面板常亮横幅 + 事件流；用户可代答（needs_user 的用户答复路径同入口） |
| 停滞成员占坑 | 领队可 interrupt + 改派；面板显示成员停留时长 |
| 链断裂未处理（站点成员被移除/长期忙碌） | 汇报与任务板高亮「下一站不可用」；领队必须偏离或追加站点后才能推进（06.7） |
| 完成即续派遗漏（成员空转） | 汇报模板自带空闲提示；任务板显示空闲时长；领队人设指派纪律强制同轮双动作 |

# 任务编排优化设计：拆解判据 · 单元合格性 · 自审与分诊纪律

**背景**：对照一份 Claude Code 任务分解提示词的研究结论，逐条比对 eTeam 当前编排实现，识别出「该不该拆」无判据、「拆出的单元合不合格」无校验、验证被折叠进成员自报完成、提示词纪律缺失四类缺口。本文自含全部定稿与规格，不依赖外部文档即可执行。

**目标**：在不改动任务状态机（8 态与转移表保持原样）的前提下，用「提示词纪律 + 一个收口硬闸」提升拆解质量与单元可验收性。

**非目标（记为将来项，见文末）**：小任务并行派发；独立验证站（链末 reviewer）。

---

## 一、拆解判据与单元合格性

### 现状缺口

- 判据全软、且只写了「怎么建」没写「该不该建」。唯一判据是领队人设里一句「单站点单成员单会话可完成，不确定就拆」；领队子代理人格通篇在讲 `parentTaskId`/`chain`/`dependencies` 怎么填。
- 单元合格性零校验。`eteams_create_task` 只做结构性检查（容器不收 chain/deps/parent、站点 `stageBrief` 非空、站点成员在班底、依赖存在且无环、父必须是容器）。`contractMd` 是**可选**参数，且不校验是否含「验收标准」段。
- 收口闸只管问询。`finalizeCommissionTask` 从 `creating` 转 `ready` 目前只校验 `questionnaire` 或 `skipQuestionnaire`——**一个零小任务的空容器也能收口开跑**。

### 定稿口径

- **拆解判据用定性判据 + 正反例，不设数量门槛**。不引入「≥N 个小任务」这类数字闸门：数字针对的是步骤数，与「小任务颗粒度」语义不等价，硬套会逼出为凑数而拆的假任务。
- **主任务必须拆**：收口时主任务下至少有 1 个未取消小任务；**允许只有 1 个**（单站点任务）。
- **成员的进一步细分不进任务表**：eTeam 的拆解只到「小任务」这一层；小任务内部怎么再拆，由成员子代理在自己会话内用自己的待办机制完成，不产生 eTeam 任务。
- **验收标准必填**：每个小任务的合同必须含非空「验收标准」段。

### 收口三合一闸（`finalizeCommissionTask`）

收口（`creating → ready`）是开跑闸，依次校验：

1. 主任务下至少 1 个**未取消**小任务（`parentId === 该主任务 && status !== 'cancelled'`）。
2. **每个未取消小任务**的 `contractMd` 含非空「验收标准」段。
3. 已问询或显式 `skipQuestionnaire`（保留现有逻辑）。

任一失败抛 `ETeamsError`，附可执行中文 hint：

| 失败项 | message | hint |
| --- | --- | --- |
| 空容器 | `主任务 N 还没有任何小任务：先 eteams_create_task（parentTaskId=N）拆解，再收口` | `主任务必须拆出至少一个小任务（单站点也行）` |
| 缺合同 | `小任务 N「subject」缺少任务合同：先用 eteams_update_task 补上含「## 验收标准」的合同` | `收口前每个小任务都要有可验收的合同` |
| 缺验收标准段 | `小任务 N「subject」的合同缺少「## 验收标准」段` | `格式：二级标题「## 验收标准」+ 非空编号列表` |

**只在收口校验，不做创建期校验**：避免同一规则在两处重复实现；代价是反馈晚一步（收口时才被打回），可接受。

### 验收标准段判定（纯函数）

放在 `src/host/model/contract.ts`（纯核，无 I/O，可单测）。语义：

- 精确匹配二级标题行 `## 验收标准`：行首 `##` 后允许空白，标题文字 trim 后**精确等于**「验收标准」；不接受 `###`、加粗或变体。
- 段内容 = 该标题行之后、到下一个 `## ` 或 `# ` 标题（或文末）之间的文本；**去空白后非空**才算有效。
- 提示词里把格式写死为上面这一种。

## 二、验证：成员自审（降级于独立验证）

### 定稿口径

- **验证主体 = 成员自审**：每个成员完工前对照合同「验收标准」逐条核对，给出证据（能跑通 / 有复现方式，而非「文件存在」），结论写进 `eteams_complete_task` 的 `output`。
- **不新增验证链站、不新增验收状态**。
- **强制度 = 纯提示词默认**，无机器闸。

### 失败回退：复用现有通道 + 「谁的问题谁修复」

自检不过且自己修不了 → 报告领队并等待分诊。领队判断是否需要问用户：需要则 `eteams_escalate_task` + 弹窗问；不需要则直接派**责任人**修复——默认派回**问题所在站的实现者**，而不是无脑回最近执行者。这是给领队分诊纪律加一条「责任归属」条款，不动状态机。

### 已知代价（记录在案）

自审的固有弱点是「自己盖章」：研究结论明确要求「只有验证者能下结论」「不能靠自己的总结自封部分完成」。本方案拿「流程简单、零成本」换「漏检风险」。若后续观察到漏检率高，升级路径是「链末 reviewer 站」——`chain` 机制已原生支持，无需改状态机。

## 三、并行执行：暂缓（将来项）

先记录一套已验证可行的最小设计，本期不实现：

- 现状：`startGroupTask` 已遍历所有 `ready/paused` 小任务尝试派发，唯一串行化来源是「已发过一棒则其余进接力队列」的单棒闸（`assignment.ts` 内）。依赖约束由派发核 `prepareAssignment` 兜底，完成续派已在 `completeTask` 尾部复跑同一函数。
- 设计：删单棒闸 → 循环自然变成「就绪即派」；循环内加 `dependenciesSatisfied` 预检，把「等待前置依赖 #x、#y」写进 skipped 原因（不再让派发核抛错刷屏）；同成员占用（`assertNotBusy`）原因改友好文案。
- 并发上限不需要配置：每个成员在同一大任务只有一行副本一个会话，天然互斥，真实并发上限 = 参与成员数。
- 提示词纪律：产物文件/改动区域重叠的小任务必须显式加 `dependencies`，否则会被并行跑。
- 数据模型已就绪，改动面很小，需要时可直接捡回。

## 四、提示词纪律（四处文案 + 一处死参数清理）

### 4a｜站点简报（`stageBrief`）质量条款

指派信带「本站简报：`<stageBrief>`」，但领队怎么写没有纪律，易出现「基于上一站发现继续做」式懒委派。补纪律：`stageBrief` 必须**自包含**——改哪些文件/区域、要达成什么、验收看哪几点；禁止「继续完成」「按上一站」这类空泛措辞。

### 4b｜完成标准的「禁止清单」

把分散在工具契约与状态机里的完成判据，提炼成成员可见的一份短禁止清单：测试在失败、实现只做一半、有未解错误、找不到必要依赖时**不得**标完成；被阻塞时新开一条描述要解决什么。并入成员自审纪律（议题二同一落点）。

### 4c｜`wait` 分诊判据

给领队的失败分诊一份可执行判据：**可自修的代码/产物缺陷 → `reassign` 派回责任人**；**需要外部条件、权限、需求变更、环境问题 → `escalate` 问用户**。与议题二的「谁的问题谁修复」合并成同一段。

### 4d｜任务名双形态 — 本期不做

`subject`（祈使式）+ 新增 `activeForm`（进行时）供面板 spinner，属展示增强、非质量闸，涉及 schema + 客户端展示，暂缓。

### 4e｜清理死参数

`assignmentMail` 的 `teamName` 入参声明了但未被使用，删除。

## 验收与测试

- **纯函数单测**（`model/contract`）：含「验收标准」且非空 → 通过；缺标题 / 标题为 `###` / 段内只有空白 → 拒绝；段后接 `### 子标题` 仍算段内。
- **收口闸集成测试**：空容器被拒；某小任务缺合同被拒；某小任务合同无「验收标准」段被拒；全部合格放行 `creating → ready`；未问询且未声明跳过仍被拒（现有用例回归）。
- **回归**：跑 `pnpm typecheck`、`pnpm lint`、`pnpm test`，确认现有 captainDispatch / sessionTeam / lifecycle 用例不破。
